- 2026-09-26 (Phase 1, ADAPT): Plan's Gemini service contract named `gemini-3.8-flash`. During manual verification (1.3/1.5) that model returned `503 UNAVAILABLE` ("high demand") on ~75% of identical requests (confirmed via direct curl against the Gemini REST API, both under its own name and the `gemini-flash-latest` alias, which resolves to the same `modelVersion`). This is an upstream availability issue, not a code defect — `ItineraryGenerationError` with `cause: "upstream"` correctly fired on every 503. Per the user's decision, `src/lib/services/gemini.ts`'s `GEMINI_ENDPOINT` was switched to `gemini-flash-lite-latest`, which returned `200` with a schema-valid plan on first try. Revisit if `gemini-3.8-flash` capacity improves.

- 2026-09-26 (Phase 1, ADAPT — scope addition): Per the user's request ("can we guard against a nonsense city?"), `itinerary-schema.ts`/`gemini.ts` gained a `city_recognized: boolean` field beyond the plan's original Phase 1 contract. The prompt asks Gemini to self-report whether the requested city is a real, recognizable place; `generateItinerary` now throws `ItineraryGenerationError` (`cause: "invalid_response"`) when `city_recognized` is `false`, before the day-count check, and strips the field back out of the returned `ItineraryPlan`. **This reverses Phase 1's own documented manual-verification item 1.4** ("Requesting an invalid/nonsense city still returns a schema-valid response ... confirms the validation layer doesn't reject on content") — that checkbox is now checked based on the *opposite* observed behavior (a nonsense city is rejected, not accepted), per the user's explicit choice of this lightweight prompt-based approach over leaving it unguarded or building real geocoding as a separate change. Flagged and confirmed correctly wired (no bypass) by `/10x-impl-review`'s Phase 1 review.

- 2026-09-27 (Phase 4, ADAPT — all confirmed by the user in chat): (a) The `GET /api/trips` fetch lives in a hook, `src/components/hooks/useTrips.ts` (CLAUDE.md: hooks go in `src/components/hooks/`), owned by the wrapper island `src/components/trips/TripsPanel.tsx`; `TripList.tsx` is presentational (plan said TripList fetches on mount itself). (b) After a save, the `POST /api/trips` 201 body (the persisted trip + points) is prepended via `addTrip` instead of re-fetching; `refresh()` re-fetches only if that body is unreadable. Reason: on `npm run dev` each API request takes ~7 s, so save + re-fetch made the new trip appear ~15 s after Accept and looked broken. This changed Phase 3's `TripGeneratorFlow` `onTripSaved` prop to `(trip: TripWithPoints | null) => void`. A ref in `useTrips` keeps locally added trips if an older in-flight GET resolves without them (impl-review phase 4, F1). (c) UI additions requested by the user: trip cards collapsed by default (disclosure button), the just-saved trip auto-expanded, scrolled into view and highlighted for 2.5 s, and an "N places" count in the card header. Still to do after Phase 4 (agreed): side-by-side layout (generator left, list right) on wide screens.

- 2026-09-28 (Phase 5, ADAPT — scope addition, requested by the user in chat): During Phase 5 e2e verification every Gemini model returned `503 UNAVAILABLE` ("high demand") on most requests (the key was also moved from depleted prepay credits to the free tier). Two changes to `src/lib/services/gemini.ts`: (a) `GEMINI_ENDPOINT` switched from the `gemini-flash-lite-latest` alias to the pinned `gemini-3.1-flash-lite` (stable, non-preview; `gemini-3.5-flash-lite` and Gemma 4 were tried and rejected — Gemma returns a `thought` part in `parts[0]`, wraps JSON in fences and takes 40 s+); (b) **this reverses the plan's "No automatic server-side retry" exclusion**: HTTP 503 is now retried up to `MAX_UNAVAILABLE_RETRIES = 5` times with a 1 s pause before the user sees the error. Timeouts, 4xx, other 5xx and network errors are still not retried. Verified live: 3 retries → 200 in 7.4 s, 1 retry → 200 in 4.0 s.
